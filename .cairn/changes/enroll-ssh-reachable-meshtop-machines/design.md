# SSH-reachable Meshtop Fleet Design

## Selection and authority

`inventory/core/machines.ncl` declares 12 machines; `inventory/dgx/generated/machines.json` declares none. Strict, noninteractive SSH from britton-desktop reached `root@100.126.162.16` (Bonsai), `root@100.108.13.4` via `tailscale nc` (the online `aspen3-1` peer), and `root@britton-desktop.clan` (the current machine). Aspen3 and desktop already have distinct running agents. Bonsai is the sole new enrolled host; it is selected by an explicit machine-level option, not a shared tag.

The other declared targets did not authenticate on the selected route: britton-fw timed out; aspen1 timed out via `.local`, RDMA and Tailnet; aspen2 was unreachable via its hostname and timed out over RDMA and Tailnet; pine and utm-vm names did not resolve; three `chv-dev` VM IPs had no route; britton-air's inventory IP had no route and its `.local` name did not resolve. Tailnet's online peer list independently showed Bonsai and `aspen3-1` but not those other declared peers. These are time- and route-scoped observations, not proof a machine is permanently off or unmanageable through a different authorized route.

## Agent, roster, and activation

Bonsai explicitly imports the Meshtop module in its machine file, reuses the current x86_64-linux package, and opts in with the pinned desktop viewer ID. The agent's private 0600 seed was created on Bonsai in its own systemd `StateDirectory`; its observed public endpoint ID is `9c71e0f64c3d068d9f6997a978d9575ca99486332ebec799b566a086b6520d66` (unchanged across the selected service restart). Never copy Aspen3's or the desktop's private seed to Bonsai, or regenerate the viewer key as part of this enrollment.

To avoid unrelated whole-system changes, the only built Bonsai output was its NixOS-generated `systemd.units."meshtop.service".unit`, with the same store path as Aspen3's generated unit under this source pin. Its closure was copied over strict authenticated SSH, pinned by `/nix/var/nix/gcroots/meshtop-agent`, and linked in writable `/etc/systemd/system.control/meshtop.service`. A second persistent link under `multi-user.target.wants` in `system.control` makes the boot target want Meshtop. After reload and start, `FragmentPath` and `ExecStart` selected the expected unit and package, the boot target's `Wants` included Meshtop, and the private key was 0600. `systemctl is-enabled` reports `disabled` because the link is outside conventional `/etc/systemd/system`; a reboot was not exercised. A later normal Bonsai Clan switch must remove **both** scoped links, reload/restart, verify the managed unit and authenticated sample, then retire the extra GC root. Do not claim a full NixOS generation switch or untested reboot continuity.

Only the desktop Home Manager-generated `hosts.toml` source and its existing `onix-roster` GC root/link changed, preserving both original IDs and the separate user agent unit and key. The sole authorized viewer process sampled all three over Iroh; the wide terminal showed all three live panels, while `j`/`k` at 80×24 reached Bonsai and returned to two still-live panels. An unrelated viewer key received no Bonsai snapshot. Stopping only Bonsai left the first two live TUI panels `ON` and Bonsai `OFF` with its previous metrics retained; a sole `watch --once` returned two fresh snapshots and only Bonsai's timeout before its service was restarted. Simultaneous TUI and one-shot processes using the same viewer identity caused the one-shot to report `dial failed` for healthy agents in this observation; it sampled all three successfully after the TUI exited. Ownership remains onix-core for inventory, generated unit, roster and scoped adoption; standalone Meshtop owns unchanged wire and UI behavior.
