# Deploy meshtop on Aspen3 and britton-desktop

## Source and package boundary

`meshtop` is an independent repository at `/home/brittonr/git/OnixResearch/meshtop`, revision `f433b38476bb6a682b53bd53458c12dd4647cfb3`. There is no published remote input yet. A repo-owned sync script copies only reviewed Cargo sources and lockfile from that exact clean commit into `pkgs/meshtop/source`; a recorded revision binds the snapshot. Nix builds solely from onix-core tracked source, never from the sibling checkout or a runtime Cargo fetch. Future upstream changes require a new revision, script import, package check, and rollout review.

## Agent and viewer authority

The desktop viewer's default key at `/home/brittonr/.local/state/meshtop/viewer.key` was generated on britton-desktop, with public Iroh ID `e4595bca7f97787646d6da8b3eab21f02e88d56759b9ac73d3a2f05c3932af51`. Only this public ID enters the services. Aspen3 imports the opt-in NixOS module and runs its agent with a 0600 identity in a private persistent systemd StateDirectory. The desktop's selected Home Manager profile installs the viewer and runs a separately keyed 0600 user agent under the already-lingering `brittonr` manager. Other machines receive neither service. These keys are not exported to Nix or copied between hosts; changing the viewer key requires changing both service policies.

The observed public agent IDs are `1513e39997fc37845f7af6421fdf1ebc47c3920123d66bd3849b934204c40339` on Aspen3 and `6751880624ae32a6dddb262599be7a867fa20994ebcebb1d0e84c4b2aa0cfc77` on britton-desktop. The desktop Home Manager roster pins both identities. A roster entry contains a public ID only; it grants no server-side access. Changing one agent key updates only that host's roster entry.

## Build and activation

The Aspen3 NixOS closure was built locally and activated through Clan with `--build-host localhost`; building on Aspen3 itself failed in Nickel Wasm evaluation. Clan observed the new system already active after retrying activation over unrelated, pre-existing Celld failures. The desktop's complete NixOS build stopped inside the locked TT-Metal 0.77.0 ELFIO 3.12 header (`uint16_t` without `<cstdint>` under GCC 16). Rather than override its read-only `/etc/systemd/system` or switch a partially built system, the exact Home Manager-rendered unit and roster were linked into the desktop user manager/config with explicit Nix GC roots; `nix profile add .#meshtop` installed the package. The selected Home Manager generation builds, but was not globally activated because its scripts would also change unrelated desktop profile state. Repair the Tenstorrent build in its owning repository before a normal desktop Clan switch. Current activation is scoped to the Meshtop artifacts, not the whole desktop NixOS profile.

## Themed GPU view and agent refresh

The viewer renders themed, numeric full and compact cards without changing the pinned two-host roster. The updated agent discovers at most 128 DRM entries, selects up to eight AMD GPUs, and samples only bounded read-only sysfs counters for busy percentage, VRAM used/total, edge temperature, and clock speed. Per-sensor absence is not a zero; absent GPU fields from an older agent are explicitly unreported. Tenstorrent accelerator cards and other vendors are not GPU telemetry sources for this revision. The authenticated read-only Iroh transport and 64 KiB response cap remain unchanged.

Both hosts expose amdgpu counters, so the new desktop viewer alone is insufficient. The planned local-build Clan update of Aspen3 and a separate full-closure build each hit a 3600-second command deadline while rebuilding unrelated locked packages. For this source-only refresh, onix-core's exact NixOS-generated Meshtop unit was built and activated through a scoped persistent systemd control path instead; britton-desktop relinked/restarted its Home Manager-generated user unit. Neither whole-host NixOS generation was switched for this GPU revision. Preserve the existing agent and viewer keys and verify both public IDs and live GPU readings through the paired route.

The updated desktop user unit resolved to the new Meshtop package and was active after `daemon-reload` and restart. An authenticated `watch --once` preserved its roster ID and observed `AMD card0` at 22% busy, 63,733,760 / 2,147,483,648 VRAM bytes, 67°C, and 2200 MHz. The still-older Aspen3 agent preserved its ID but returned `gpus: null`, not a fabricated zero. The installed viewer displayed both hosts at 120×30 and 80×24; the compact mixed-version screen showed desktop GPU/VRAM readings alongside Aspen3's explicit "GPU telemetry not reported".

The Aspen3 unit `/nix/store/4gzrcx4rkmkk33ddxz2zg65x8hr270d2-unit-meshtop.service` references the new Meshtop binary while retaining the declared DynamicUser sandbox and private key path. Nix copied only that generated unit and its package through the authenticated Tailnet SSH route; Aspen3's configured auto-GC ran during transfer, so `/nix/var/nix/gcroots/meshtop-gpu-agent` pins the closure. The writable `/etc/systemd/system.control/meshtop.service` link selected this exact generated unit over the previous read-only NixOS unit. After a Meshtop-only reload/restart, systemd reported it active with the new `ExecStart`. An authenticated `watch --once` then returned unchanged host IDs and both AMD GPUs: Aspen3 card1 0% measured idle, 1,297,805,312 / 4,294,967,296 VRAM bytes, 42°C, 602 MHz; desktop card0 5%, 63,733,760 / 2,147,483,648 bytes, 67°C, 2200 MHz. The installed viewer displayed both GPU panels at 120×30 and 80×24 with no host selection.

This is a bounded one-time exception for the unrelated full-closure rebuild, not a completed Aspen3 generation switch or proof of reboot continuity. Onix-core owns the control link and GC root. Revisit when the local-build Clan update succeeds: remove that higher-priority link, reload/restart, confirm the new NixOS-managed `ExecStart` and live GPU sample, then retire the extra root. Future Meshtop pins must repeat the exact unit build/copy or finish the normal Clan cutover; the pinned binary alone does not refresh either agent.

The immediate consumer is this paired desktop view of Aspen3 and britton-desktop. The standalone Meshtop repository owns the bounded collector, wire field, and renderer; onix-core owns its exact source pin, both service definitions, and operator rollout. Repeat the source tests, `scripts/sync-meshtop.sh` import, `nix build .#meshtop`, the scoped service activation, and authenticated two-host `watch --once` after a source update. Package or system evaluation alone cannot establish live GPU sensing.

## Rollback and non-claims

Disabling Aspen3's `services.meshtop.enable` and redeploying, or disabling the desktop user service, stops the corresponding agent without deleting its private identity; restoring it retains the same endpoint ID. When the desktop's full NixOS/Home Manager generation can be switched, remove the temporary artifact GC roots and redundant Nix-profile entry only after the managed user unit takes over. A flake evaluation, built derivation, active unit, or relay registration alone is not proof of live metrics; the paired viewer obtained both named hosts' samples, an unpaired viewer was denied, and the healthy host remained readable when the other agent was stopped.
