## Upstream defect: omnibin-shell leaks its daemon

After `omnibin-shell` exits, its `omnibin mount` daemon keeps running, and both
FUSE mounts stay under `$XDG_RUNTIME_DIR`. A manual `SIGTERM` does not stop it
either. `strace` of the main thread shows the signal arriving and the thread
resuming the same `FUTEX_WAIT_BITSET` on its parker, still in the parked state
(`0xffffffff`), with no wake:

```text
--- SIGTERM {si_signo=SIGTERM, si_code=SI_USER, ...} ---
futex(0x5e4ed37b6e38, FUTEX_WAIT_BITSET_PRIVATE, 4294967295, NULL, FUTEX_BITSET_MATCH_ANY
```

Cause: `src/main.rs` handles the signal by calling `Sender::send` on an
`std::sync::mpsc` channel that the main thread waits on with `recv()`. The
kernel delivers the signal on that same main thread, and std's
`mpmc::waker::Waker::try_select` skips entries that belong to the current
thread. The message is queued, but the receiver is never unparked.

What the next `omnibin-shell` does: its stale-mount cleanup runs the
non-setuid `fusermount3` from `pkgs.fuse3`, because `runtimeInputs` puts it
ahead of `/run/wrappers/bin`, so the cleanup fails. The new daemon then fails
with `failed to access mountpoint ... Permission denied`, and the shell
carries on using the old daemon's mount. Commands still run. Cleanup is
`pkill -KILL -f 'omnibin mount'`, then `/run/wrappers/bin/fusermount3 -u -z`
on `$XDG_RUNTIME_DIR/omnibin` and `$XDG_RUNTIME_DIR/omnibin-store`.

## Limits

This evidence shows that both commands are installed on `britton-desktop` and
that a historical binary runs in the namespace while the host store is left
unchanged. It does not show that any other fetched package is correct, it does
not bound `~/.cache/omnibin`, and it does not fix the upstream daemon leak.
