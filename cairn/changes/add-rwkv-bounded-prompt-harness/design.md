## Context

The pinned text harness already owns the exact checkpoint, seven tokenizer/model/generation artifacts, exhaustive byte vocabulary, wrapper special-token behavior, twelve-layer recurrent state, direct BF16 head audit, and zero-state replay. It intentionally accepts no arguments and runs only `Hi`. The new interface must reuse those authorities without permitting caller-selected model paths, tokenizer files, templates, devices, or execution backends.

The checkpoint's remote `modeling_rwkv7.py` delegates to FLA. The model card pins `flash-linear-attention==0.3.0`; that runtime routes RWKV7 through Triton GPU kernels and its own layer source warns that the implementation may be buggy. Therefore direct FLA/Transformers execution is not a valid CPU authority here. A separate PyTorch CPU translation of the pinned FLA schema and official RWKV recurrence equations can provide bounded equation-reference comparison, but it must not be described as FLA runtime or official-runtime parity.

## Goals and evidence contract

The exact goal is a deterministic caller-supplied UTF-8 chat-message path with explicit resource bounds, plus a complete-tensor numerical comparison against a pinned CPU PyTorch equation reference. Completion requires positive and negative request evidence, byte-identical repeated receipts, exact tokenizer/chat-template behavior, retained-state replay controls, exact PyTorch/Rust top-two ranking, complete final-hidden/logit/recurrent-state comparisons under named tolerances, pinned source identities, and clean Rust/Nix/Cairn checks.

False completion includes accepting implicit or excessive limits; accepting caller-selected files or backends; silently truncating prompts; replacing exact generated bytes with lossy text; comparing only selected token IDs; using the Rust implementation as the PyTorch implementation; treating model agreement as official-runtime, FLA-runtime, hardware, or general-correctness proof; or counting an advisory/model review as validation.

## Bounded request design

`rwkv-prompt-harness` accepts exactly these required named arguments, in any order:

- `--message <UTF-8 text>`
- `--max-prompt-tokens <positive integer>`
- `--max-new-tokens <positive integer>`

The pure parser rejects missing, duplicate, unknown, valueless, non-integer, zero, and excessive arguments. The request core names package caps for message bytes, rendered prompt tokens, and generated tokens. The caller's prompt-token limit must not exceed the package cap, and the rendered prompt must fit both; failure is explicit rather than truncating. The generation limit must not exceed the package cap. The shell converts OS arguments to UTF-8, reads only build-time embedded regular Nix-store files, invokes the pure core, and emits one JSON receipt.

The exact pinned chat template renders `<|rwkv_tokenizer_end_of_text|>User: {message}\n\nAssistant:`. Wrapper special IDs remain visible. Generated IDs always produce exact token-byte evidence. If the bounded byte sequence is incomplete UTF-8, the receipt records that fact and leaves decoded text absent; it never substitutes lossy text. Generation-config EOS ID `0` stops immediately and contributes no ordinary token bytes.

## Functional core and imperative shell

The library owns deterministic argument-token parsing, numeric bound validation, prompt rendering, tokenization, model execution, replay, state discrimination, byte accumulation, UTF-8 classification, and receipt construction. `src/bin/rwkv-prompt-harness.rs` owns only OS argument collection, embedded Nix-store file reads, error plumbing, and JSON stdout. Existing fixed-text execution calls the same internal model core and then reconstructs the historical fixed receipt shape so accepted output remains stable.

## PyTorch equation-reference comparison

A dedicated argument-free Rust fixture binary emits the accepted prefix `[1, 2]` plus complete FP32 final-hidden, logits, and flattened recurrent matrices from the pinned checkpoint. It accepts no model or output path. A repository-owned Python program is justified only as the PyTorch framework adapter: it loads the same Nix-store safetensors, follows the separately structured pinned FLA schema and official RWKV recurrence equations, and compares every emitted element. It has a functional calculation/comparison core and a thin argument/file/JSON shell.

The Nix comparison derivation owns all process orchestration and provides only pinned store paths. It pins and checks the checkpoint's Hugging Face delegator, FLA v0.3.0 RWKV7 layer, and an exact official RWKV demo revision. The comparison requires exact tensor inventory and orientation, exact top-two IDs with the lowest ID winning ties, finite values, and named maximum absolute tolerances for final hidden, logits, and recurrent state. A deliberately changed fixture and malformed fixture must fail.

## Risks and mitigations

- **Caller input expands work**: explicit caller limits and lower package hard caps fail before model execution.
- **Token limits are confused with byte limits**: both are separately named and reported; no truncation occurs.
- **Special-token text appears in user content**: exact wrapper tokenization is recorded rather than sanitized or reinterpreted.
- **Generation ends in partial UTF-8**: exact bytes remain authoritative and decoded text is optional.
- **Framework arithmetic differs by reduction order**: comparison uses named finite tolerances and reports complete-vector maximum deviations, while top-two IDs must match exactly.
- **Reference adaptation copies the implementation bug**: source authorities come from separate repositories and the Python program uses tensor operations rather than Rust scalar loops; nevertheless it remains an equation adapter, not independent official-runtime proof.
- **Large framework dependencies enter the runtime package**: PyTorch exists only in a separate Nix check derivation and is absent from the installed Rust package closure.
- **Hardware boundary is violated**: source and Nix checks reject CUDA/device selection, Tenstorrent nodes, Metalium, subprocess calls from Rust, retries, and owner-control surfaces.
