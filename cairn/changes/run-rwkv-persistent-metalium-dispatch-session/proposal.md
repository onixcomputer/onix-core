# Proposal: Run one persistent Metalium RWKV dispatch session

## Problem

The accepted persistent dispatch receipt proves strict third/fourth-token lifecycle, same-layer state continuity, canonical request/response framing, and full-model composition only with a device-free CPU transport. It does not prove that one Metalium owner can remain open while physical ttWKV7 responses are consumed by the host model to derive later-layer and fourth-token requests.

## Proposed change

Prepare, validate, and consume the user's newly approved single device-1 attempt through one immutable argument-free runbook. A Rust host shall retain the 12-layer model state and drive exactly twenty-four canonical calls through one persistent C++ child. The child shall initialize one Blackhole MeshDevice, enforce exact sequence/call/token/layer authority, execute one production DecodeL enqueue per request, return request-bound BF16 responses, prove twelve same-layer physical state continuities, and close after the reviewed call budget. The host shall consume each physical response before preparing the next request and shall compare every response and both completed token outcomes with the independent BF16 oracle.

Owner isolation, an independent rollback timer, fixed timeout and health windows, complete raw evidence, terminal classification, and no-retry accounting shall remain mandatory. Tasks `30` and `64` and evidence roots `/var/tmp/rwkv-ttwkv7-boundary-device-1` and `/var/tmp/rwkv-ttwkv7-boundary-device-2` remain immutable and unusable.

## Impact

A successful safe receipt would establish one persistent physical ttWKV7 transport over all twelve layers of two consecutive model tokens, including physical response consumption and retained matrix-state carry. It would not establish a wholly device-executed RWKV layer/model, exact BF16 parity, general P150 compatibility, serving, throughput, latency, or an owner-safe result unless restoration meets the predeclared health window.
