## Clan deploys
- Bare `aspen1` is not reliably resolvable from managed hosts. Use `aspen1.local` for SSH deploy targets and runtime URLs (`root@aspen1.local`, Lemonade API bases) unless a specific network path requires another name. Harmonia's extra substituter is one such exception: use `http://100.100.103.95:5000` so nix-daemon does not depend on mDNS.
- On this workstation, `clan machines update ...` can lose vars generator `finalScript` store paths to local auto-GC mid-run (`/nix/store/...-generator-...: No such file or directory`). If that happens, rerun the deploy with `NIX_CONFIG=$'min-free = 0\nmax-free = 0'` so the generator script survives long enough to execute.
- Changing a vars generator's output does not automatically rewrite already-generated shared vars. If a deploy still sees stale generator content, run `clan vars generate <machine> --generator <name> --regenerate` first, then deploy again so the updated secret files are synchronized.
- Removed vars-generator outputs can linger too. After switching a generator from one output file shape to another (for example `env-file` -> `auth-json`), manually delete orphaned `vars/shared/<generator>/...` files that the new generator no longer declares.
- Unset clan prompt secret files can decrypt to the stock SOPS placeholder text `Welcome to SOPS! Edit this file as you please!` rather than an empty string. Treat that placeholder as "unset" when auditing or migrating vars.
- `vars/shared/.../secret` files are stored as raw secret blobs (`{"data": "ENC[...]", ...}`), not schema-aware JSON payloads. If you hand-edit a structured secret like `auth-json`, re-encrypt the whole plaintext file with `sops encrypt --input-type binary --output-type json ...`; encrypting nested JSON fields makes `sops-install-secrets` fail with `error emitting binary store: no binary data found in tree`.
- If `clan machines update ... --upload-inputs` fails in `nix flake archive --to ssh://...` with `sized: unexpected end-of-file`, check the named source path with `nix-store --verify-path`. Legacy `ssh://` store copying can hide the real `hash mismatch importing path` when a local fixed-output flake input was modified/corrupted. Clean any invalid partial target path with `nix-store --delete --ignore-liveness`, prefetch the same locked input on the target (`nix flake prefetch github:owner/repo/rev`) so upload skips the corrupt local stream, then repair the local store as root later.
- Clan parses a `deploy.buildHost` without a user as `root@`. `root@britton-desktop` has no GitHub key, so evaluating octet's GitHub-SSH cargo dependency (`bounded-exec`) fails there with `Permission denied (publickey)`. aspen3 therefore builds as `brittonr@britton-desktop`; aspen1, aspen2, pine and the Cloud Hypervisor VMs still name the bare host.
- Units attached under `/etc/systemd/system.control` outrank the generation's `/etc/systemd/system` units, and Home Manager renames hand-installed files it takes over to `.hm-bak`. Before a Clan switch takes over such a unit or file, move the attachment aside with a backup.
- aspen3 deploys run over a remote Wi-Fi tailnet path, and Clan's SSH sets no keepalive; one step stalled for 50 minutes after the closure copy. aspen3 also runs Nix with `min-free = 100 GiB` and has about that much free, so a substitution there can auto-GC a copied closure before activation. Before rerunning a stalled deploy, compare aspen3's `/run/current-system` with the built toplevel, and root that toplevel with `nix-store --add-root /nix/var/nix/gcroots/<name> --realise <toplevel>`; delete the root after the switch.
- `switch-to-configuration` on aspen3 exits 4 while `/mnt/usb4-nvme` is absent, because the RustFS-backed celld units fail. Clan logs `activation returned 4 — retrying`, then accepts the switch when `/run/current-system` matches.

## Flake evaluation
- Reuse `self.lib.machines.definitions` for raw machine metadata (including `system` and `addresses`), or `self.lib.machines.names` / `hasTag` for queries. NixOS tags receive that same shared value as `nclMachines`; do not independently re-evaluate `inventory/core/machines.ncl`. The Clan inventory strips the tooling-only fields at its own projection boundary.
- `nix flake show --all-systems` fails in this repo unless you pass `--option allow-import-from-derivation true`; the `wasm-plugins` checks evaluate nix-wasm plugin derivations during flake evaluation.
- Keep the `nix` flake input pinned at or below cachix/nix rev `88579a87` (devenv-2.35, 2026-07-22) until upstream removes `packaging/patches/0001-Fix-uncaught_exceptions-not-accounting-for-forced_un.patch` (added in f8b102f9). That local patch duplicates nixpkgs' own boost `58832123` backport; applied before nixpkgs' `0921b9f` (BOOST_NOINLINE) patch it breaks `patch` on `boost/context/fiber_fcontext.hpp`, so boost 1.89.0 cannot build and every machine deploy fails. nixpkgs already carries the same fix, so the upstream patch is obsolete. A blanket `nix flake update` that advances `inputs.nix` past f8b102f9 re-introduces the deploy failure.
- The same conflict also blocks the nixos-26.05 channel: `b5e044308f12` (2026-08-02) backported the `0921b9f`/`58832123` pair to release-26.05, which builds boost 1.89.0. `inputs.nix.inputs.nixpkgs` is therefore pinned to the immutable `nixos-26.05.4193.a50de1b7d8a5` snapshot in `flake.nix` instead of the moving `channels.nixos.org` tarball, so a lock update cannot silently move the fork onto a broken channel. Audit any future bump with the nixpkgs multiverse before pinning: `nix eval --raw github:fzakaria/nixpkgs-multiverse#multiverse.x86_64-linux.releaseTips."26.05".rev` resolves the current channel tip, and `nix eval github:fzakaria/nixpkgs-multiverse#multiverse.x86_64-linux --apply 'mv: (mv.at "26.05").boost.version'` must not report a version in the 1.88-1.92 range while the fork keeps its local patch. Once the fork drops the patch, pin the multiverse-resolved tip commit directly.
- Machines take `radicle-node` and `radicle-httpd` from the flake packages in `flake-outputs/tools.nix` through the `shared-nix.nix` overlay. adios-flake builds those from a bare `import nixpkgs { inherit system; }`, so a machine's `nixpkgs.config` cannot exempt them. nixpkgs marks radicle-node insecure after Radicle's 2026-09-23 transport disclosure; the operator accepted that risk, private repositories included, and `tools.nix` permits exactly `radicle-node-1.10.3`. When nixpkgs moves radicle-node, evaluation of aspen1, britton-desktop and aspen3 fails again until the new version is reviewed.
- The `creative` tag sets `nixpkgs.config.allowInsecurePredicate`, and nixpkgs then ignores `permittedInsecurePackages`. On creative hosts (aspen3, britton-desktop) a module's `permittedInsecurePackages` entry has no effect unless the tag's predicate list also names the package.

## Package pinning (nixpkgs-multiverse)
- The `multiverse` input (github:fzakaria/nixpkgs-multiverse) is wired into every NixOS machine (`inventory/tags/nixos.nix`), the darwin machine (`machines/britton-air/configuration.nix`), and every home-manager profile (`modules/home-manager-profiles`, via `sharedModules`). Options are lazy: importing the module costs nothing until a pin is forced.
- Pin a package version with `multiverse = { enable = true; pins.ripgrep = "13.0.0"; };`. Pins install derivations from other nixpkgs revisions; they suit leaf tools, not libraries other packages link against. Only top-level attributes exist in the index — `python3Packages.*` cannot be pinned.
- A pin brings its revision's closure, so unfree pins need `multiverse.config.allowUnfree = true` (the module's revisions do not inherit the host's `nixpkgs.config`).
- `config.multiverse.plan` reports how pins divide across revisions without fetching anything; `assertions = [ { assertion = config.multiverse.plan.revisions == 1; message = config.multiverse.plan.why; } ];` enforces one-revision consistency.
- Cost is per revision touched. `minimize` (default) groups pins onto the fewest revisions that can serve them; `mvs solve` explains the same plan from the CLI.
- Per-package locks live in the repo-root `multiverse.lock` (format maintained by `mvs`, excluded from treefmt via `*.lock`). It is wired into every NixOS machine, the darwin machine, and every home-manager profile; entries install nothing until `multiverse.enable = true` is set, and resolve as `config.multiverse.locked.<attr>` meanwhile. Workflow inside `nix develop`:
  - `mvs lock add <attr>[@ver]` — pin a package (newest indexed version when `@ver` is omitted)
  - `nix flake update multiverse && mvs lock update <attr>` — move exactly one pin forward (two steps on purpose: the pin cannot name a revision the input does not know)
  - `mvs lock status` — how far behind each pin has fallen, offline
  - `mvs lock minimize [--check]` — collapse pins onto the fewest revisions; `--check` fails CI on drifted locks
- `flake-outputs/_multiverse-checks.nix` verifies module wiring offline (plan resolution, install counts, duplicate-claim assertion, pin type check, repository lock parse, lock-version rejection).

## Packaging
- Custom packages live in onixpkgs (`/home/brittonr/git/OnixResearch/onixpkgs`). `inventory/tags/common/shared-nix.nix` applies its overlay to every NixOS and darwin machine, `modules/dgx-machine` applies it to DGX machines, and `flake-outputs/checks.nix` applies it to check harnesses. - The `onixpkgs` input fetches `git+ssh://git@github.com/OnixResearch/onixpkgs.git`, like the other OnixResearch inputs. After pushing a package change to onixpkgs `main`, run `nix flake update onixpkgs` here and evaluate the machines that use the package.
- nixpkgs' GCC 16 stdenv (seen at nixpkgs `b6c8664`, 2026-09-29) rebuilds zig 0.16.0 into a compiler whose `compiler_rt.o` carries `.eh_frame` FDEs against section symbols with no section; the earlier GCC 15 build of the same zig did not. A Zig static library that bundles compiler_rt then fails ld.bfd links with `.eh_frame_hdr refers to overlapping FDEs`. Stop bundling it (`bundle_compiler_rt = false`) or link the shared library; `inventory/tags/common/shared-nix.nix` does the former for herdr's libghostty-vt.

## Rust workstation config
- `britton-desktop` manages `~/.cargo/config.toml` through the `inventory/home-profiles/brittonr/kache` Home Manager profile. Preserve `target-dir = "/home/brittonr/.cargo-target"`, `net.retry = 3`, and `term.quiet = false` when changing that profile.
- Build storage on `britton-desktop` is ZFS-backed and quota-limited: `datapool/cargo-target` mounts at `~/.cargo-target`, `datapool/git` mounts at `~/git`, and interactive Kache data uses `/var/cache/kache-nix/user-brittonr`. - `machines/britton-desktop/build-storage.nix` removes ignored Cargo targets only after 21 days without modified files and skips cleanup while Cargo or rustc is active. Preserve the `CACHEDIR.TAG` and Git-ignore safeguards when changing retention.
- `SCCACHE_IGNORE_SERVER_IO_ERROR=1` on stock `sccache` is not enough for dead-transport startup/connect failures like a broken `SCCACHE_SERVER_UDS`; `sccache rustc -vV` can still abort before local fallback. For Home Manager Cargo rollouts here, use an outer rustc-wrapper that can detect those transport failures and exec real `rustc` directly.
